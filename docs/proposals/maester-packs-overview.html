How it works

Maester Packs works the way skills.sh works for agent skills. Nobody submits anything. You push a pack to a public GitHub repository; the first time someone installs it, Maester Packs fetches the repository itself, checks and scans it, and lists it. Admins install packs with one command, connect to the platform through Connect-Maester, and see the results in their Maester report next to the built-in checks.

YouPush and tagA pack in a public GitHub repository
AnyoneInstall onceInstall-MtPack pins the exact commit
Maester PacksFetch, scan, listRisk level and badges, usually within the hour
AdminsConnect and runResults in their report, in a Packs section

For pack builders

Write the same native tests you write for Maester 3.0, add a connector if your platform needs one, tag a release. No form, no approval queue.

For admins

Every pack shows a risk level and who published it before you install. Nothing updates on its own, and CI runs exactly what your lock file says.

For security teams

Packs are pinned, scanned on every version, kept apart from the built-in checks in the report, and can be stopped everywhere with a signed blocklist.

Part 1

Build a pack

If you can write a Maester custom test, you can write a pack. A pack is a Maester 3.0 test suite with a manifest, published from GitHub.

Anatomy of a pack

github.com/contoso/maester-google-workspace
maester-pack.json                  # the manifest
README.md                          # shown on your pack's page
LICENSE
icon.svg                           # optional
connectors/
  GoogleWorkspace.ps1              # optional: signs in to your platform
tests/
  suite.json                       # a Maester 3.0 suite
  Test.MP.CNT.0001.ps1             # one test: a function with [MaesterTest(...)]
  Test.MP.CNT.0001.md              # its description and remediation
helpers/
  Invoke-GwsRequest.ps1            # functions your tests and connector share
.github/workflows/pack-scan.yml    # optional: our scanners on every push

The manifest is plain data. Nothing in it runs. It names your pack, your code, your suites and connector, and declares everything your pack reaches.

maester-pack.json (trimmed)
{
  "Id": "contoso.google-workspace",
  "Name": "Google Workspace security baseline",
  "Version": "1.2.0",
  "Publisher": "contoso",
  "Code": "CNT",
  "RequiresMaester": ">=3.1 <4.0",
  "SecurityContact": "security@contoso.com",
  "Suites": ["tests"],
  "Connectors": [{
    "Service": "CNT.GoogleWorkspace", "Platform": "GoogleWorkspace",
    "File": "connectors/GoogleWorkspace.ps1",
    "Connect": "Connect-GwsService", "Test": "Test-GwsService"
  }],
  "Uses": {
    "Services": ["CNT.GoogleWorkspace"],
    "GraphScopes": [], "TenantWrites": [],
    "Network": ["admin.googleapis.com", "oauth2.googleapis.com"],
    "Modules": []
  }
}

A test is a native Maester 3.0 test: one function with a [MaesterTest] attribute, returning $true when it passes. The engine handles connections, errors and skips, so the test is just the check.

tests/Test.MP.CNT.0001.ps1
function Test-GwsTwoStepVerification {
    [MaesterTest(Id = 'MP.CNT.0001', Title = '2-Step Verification is enforced for all users',
                 Severity = 'High', Service = 'CNT.GoogleWorkspace')]
    [CmdletBinding()]
    param()
    $settings = Invoke-GwsRequest -Path '/admin/directory/v1/customer/my_customer/policies'
    Add-MtTestResultDetail -Result "2-Step Verification: $($settings.twoStepEnforced)"
    $settings.twoStepEnforced
}

Your code and test IDs

Every pack test ID is MP.<code>.<number>. MP stands for Maester Pack, so anyone can tell from an ID alone that a test comes from a pack, and from whom. A pack can never use a built-in ID such as MT.1001.

  • Your code belongs to you, the GitHub user or organisation, and all your packs share it. It is 2 to 5 letters or digits and starts with a letter: CNT, NWT, FAB1.
  • The first index claims it. There's no form. Put the code in your manifest; the first time any of your repositories is indexed, the code becomes yours for good. Check first with Find-MtPack -Code CNT or packs.maester.dev/codes/CNT.
  • Known brands are reserved. Codes such as GOOG, OKTA or MSFT come from public brand lists and can't be claimed, unless you are that company: then contact us and we assign it.
  • IDs are permanent. Your IDs end up in people's configs and result history, so an ID always means the same check. Don't reuse a number for a different check; give new checks new numbers. With several packs, keep them apart with a segment per pack (MP.CNT.GWS.0001) or number ranges.

Connectors

If your platform needs a sign-in, your pack provides a connector: a few PowerShell functions named in the manifest. Connect-Maester calls them, so admins connect to your platform the same way they connect to Microsoft 365.

FunctionRequiredWhat it does
ConnectYesSigns in (browser, device code or unattended) and stores what your tests need with Set-MtConnectionState. Its parameters become the connector's settings.
TestYesReturns $true when connected. Maester uses it to skip your tests cleanly when nobody connected.
DisconnectNoCalled by Disconnect-Maester.
DescribeNoReturns non-secret facts (domain, customer ID, edition) for the report header and Get-MtTenantContext.
RenewNoRefreshes your platform's token before it expires, so long runs keep working.
What admins type
Install-MtPack contoso/maester-google-workspace
Connect-Maester -Service Graph, GoogleWorkspace     # browser sign-in for both
Invoke-Maester                                      # built-ins and MP.CNT.* in one report

# Unattended (CI): settings and secrets come from environment variables
$env:MAESTER_CNT_GOOGLEWORKSPACE_ADMINEMAIL = 'admin@contoso.com'
$env:MAESTER_CNT_GOOGLEWORKSPACE_CREDENTIAL = '<service account key from a secret>'
  • Name your service with your code, as in CNT.GoogleWorkspace. Bare platform names (GoogleWorkspace, Okta) are kept for official and brand-owned connectors. Admins can still type the platform name when only one installed connector serves it. Because the name carries your code, your connector never receives secrets meant for someone else's.
  • Secrets never come from the config file. Settings typed as [securestring] or [pscredential] come only from parameters, environment variables or a SecretManagement vault.
  • Write code that works in any execution model. Reach Microsoft services only through Maester's commands (Invoke-MtGraphRequest and friends), reach your platform only through your connector's state, and keep no global state between tests. Then your pack runs unchanged if packs are isolated in containers later.
  • Share a connector across packs. A connector pack lists the helpers it shares in Exports; other packs declare it in Requires and use it.

Microsoft permissions your pack needs

Maester connects to Microsoft Graph with read-only scopes. If your pack needs more, list them in Uses.GraphScopes. They are shown before install and only requested when an admin asks for them with Connect-Maester -IncludePackScopes. When a token lacks a scope, your tests are skipped with reason MissingScope rather than failing. Anything that changes a tenant goes in Uses.TenantWrites; a write scope or a declared write makes your pack High risk. A check pack shouldn't need to write.

What you can ship, and its risk level

Ship anything a GitHub repository can hold, including proprietary libraries under any licence. What you ship sets your pack's risk level, which every admin sees before installing.

RiskWhat sets itWhat installers see
LowText files only (PowerShell, Markdown, JSON), and every scan passedThe normal install prompt
MediumReadable code with findings to check: Invoke-Expression, script blocks built from strings, URLs built at run time, starting processes, script-only Gallery modulesThe findings, before they confirm
HighCompiled code (DLLs, executables, compiled Python) in the pack or its modules, archives or encoded content we can't scan, or any tenant writeEvery such file named with its hash and signer; they type the pack ID to confirm
BlockedA malware match, or confirmed malicious by a maintainerInstall refused; already installed copies stop running

A few rules every pack must follow to be listed:

  • Script files hold only function definitions. Nothing may run when a file is loaded; load libraries from inside functions.
  • Declare everything you reach in Uses: services, network hosts, Graph scopes, tenant writes, Gallery modules (pinned to exact versions). Code that reaches something undeclared is not listed.
  • Don't use tags or suite names that belong to the built-in checks, such as CIS or Maester. Pack results always appear in their own section of the report.
  • Include a SecurityContact and a LICENSE. No symbolic links, no paths that differ only in case, at most 50 MB per pack.

Publish in four steps

  1. Scaffold it

    Creates the manifest, a suite, a sample test, a connector skeleton, a README and the scan workflow.

    New-MtPack -Id contoso.google-workspace -Code CNT -Service CNT.GoogleWorkspace

  2. Write and check tests

    The same commands as custom tests. Test-MtPack runs the exact checks and scans the index runs, so you see your risk level before you release.

    New-MtTest -Id MP.CNT.0001 -Path ./tests
Invoke-MtTest -Path ./tests/Test.MP.CNT.0001.ps1
Test-MtPack -Path .

  3. Claim your code

    Check it's free, then request indexing from packs.maester.dev to claim it straight away (it works before your first release), or let the first install claim it.

    Find-MtPack -Code CNT

  4. Tag a release and install it once

    Turn on GitHub's immutable releases. The first install tells the index about your pack; it is usually listed within the hour.

    git tag v1.0.0; git push origin v1.0.0
Install-MtPack contoso/maester-google-workspace -AllowUnlisted

Keeping a pack healthy

  • Releases wait 72 hours before they are offered by default, so a release from a hijacked account can be caught first. Admins can install a newer one on purpose.
  • Deprecate or yank from your own manifest: "Deprecated" with a replacement, or "Yanked" for a broken version. Delisting never breaks people who already have your pack.
  • What you can rely on: a published list of Maester commands and contracts for packs, changed only with a deprecation window. The index re-checks listed packs against each new Maester release and tells you if something you use was removed.
  • If your repository disappears, Maester skips your pack with a warning in the report. Maester Packs keeps no copies of your repository.
  • Want issues instead of watching your status page? Add "Notify": "Issues" to your manifest.

Part 3

How listing works

ClientInstall eventAnonymous: source, commit, pack ID, a random install ID. Never for private repositories.
Cloudflare WorkerCount and queueDeduplicates installs and queues new repositories
GitHub ActionsScanAn untrusted job with no secrets fetches the repository itself and scans it
GitHub ActionsSign and publishA protected job signs the index and deploys static pages
  • The index trusts nothing the client says except the repository name. It fetches the release itself and checks the commit belongs to that repository.
  • Ranking is by installs: all time, trending (24 hours) and new. Installs rank packs; they never change a risk level or a badge.
  • Badges show who published a pack: Official (the Maester project), Microsoft MVP (the GitHub account is on a public MVP profile), and GitHub-verified organisation.
  • Gaming is made expensive: one install per install ID and per hashed IP per pack per day, rate limits, account age of 30 days, one new pack per owner per day, duplicates hidden, reports through GitHub accounts.
  • It costs almost nothing: static pages on Cloudflare, a small Worker and database, and free GitHub Actions minutes on a public repository. About $0 at launch, $5 a month once traffic passes the free tier.

Part 4

Security model

Packs run with the connections of a security administrator, often unattended in CI. The design assumes some packs will be malicious and some publisher accounts will be compromised, and limits what one bad pack can do.

Before anything runs

No code runs at install. Every version is pinned to a commit, a content digest and GitHub's numeric repository ID, checked on every load. Commits from forks are refused.

One gate

Every command that loads pack code, Connect-Maester included, checks the digest, the policy and the blocklist first.

Nothing changes quietly

No automatic updates, a 72-hour cooldown, and a new approval when a pack reaches more or its risk rises.

Can't pose as Maester

Pack IDs start with MP., built-in tags and suites are off-limits, and results are shown and scored apart.

Stopped everywhere

A signed blocklist, with serial numbers and expiry, stops a bad pack on every machine at its next run. It never deletes anything, so a mistake is undone at the next run.

Honest about limits

Code in the Maester session can use its connections. The prompt says so, and containers for untrusted packs come in a later phase.

What we propose

Outside tools run as their own step

A tool like TestimoX runs on its own, by the admin or in a CI job inside the network, and writes its assessment file. The pack's connector only reads that file: no sign-in, no line of sight to domain controllers, nothing launched by Maester. It checks the file's schema version and age (stale files are rejected with a reason) and reports the target, collection time and coverage. The pack stays text only, so Low risk.

Module-backed packs

A publisher can keep all their code in their own PowerShell module. The pack becomes a small static shell: a manifest naming the module, a catalog file the publisher generates from their module at build time, and docs. Maester lists and selects tests from those files without running code, then imports the module only when its tests run and calls a small, versioned API for the selected IDs. Results are accepted only for IDs in the pack's catalog.

Maester never installs modules

A pack names the modules it needs; the user installs them through their own channel. The site and the terminal show a command Maester generates, so publishers can't inject commands. If a module is missing or the wrong version, that pack's tests are skipped with the command in the warning, and the run continues.

Setup instructions from the publisher

A Setup tab on the pack page and "Next steps" after install explain how to install and run the outside tool, with a CI example. Setup text is labelled as from the publisher, never run by Maester, and scanned for download-and-run commands.

Rule catalogs

Many rules can share one evaluator: rules are declared in a static catalog instead of one test file each. Every rule is listed, selectable by ID and shown as not run when unselected. Per-target results keep the rule and the target as separate fields.

Coverage as its own result

Health and coverage get their own panel in the report. A rule whose data wasn't collected is skipped as "not collected", never failed. An opt-in switch lets CI fail on incomplete coverage.

Your own libraries, and gather once

"Reach Microsoft only through Maester's commands" becomes a recommendation. A pack that signs in with its own library, such as EntraAuth, wraps that sign-in as a connector so Connect-Maester drives it and it's declared. A run-scoped cache lets one helper gather data once for many tests.

Permissions and targets beyond Graph

Packs can declare Entra roles, Azure RBAC (for example Log Analytics Reader on a workspace) and Exchange roles, shown before install. Missing access skips the tests with a reason. A connection can be pointed at one resource in config, a test at its own resource through a parameter, and several resources through a family.

maester-pack.json for a module-backed pack (proposal)
{
  "Id": "testimox.ad-assessment",
  "Code": "TMX",
  "RequiresModules": [ { "Name": "TestimoX", "MinimumVersion": "2.3" } ],
  "Provider": { "Module": "TestimoX", "ApiVersion": 1 },
  "Catalog": "catalog.json",
  "Setup": "docs/setup.md"
}
What users see (generated by Maester, not written by the publisher)
Install-Module TestimoX -MinimumVersion 2.3 -Scope CurrentUser

This also simplifies the design: Maester no longer saves Gallery modules into its own store, pins their whole dependency tree, or needs an allowlist of well-known modules, because those modules never become part of a pack.

Still open

  • The names and shape of the provider API (catalog export, status and coverage, running the selected checks), and how it is versioned.
  • The default maximum age of an assessment file.
  • Whether rule catalogs and module-backed packs ship in phase 1, since integrations like TestimoX are ready to build on them.
