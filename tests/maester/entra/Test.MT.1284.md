High-risk agents should not be left unremediated in Entra ID Protection.

Entra ID Protection rates the risk of agents (Microsoft Entra Agent ID) and tracks a risk state for each flagged one. This covers agent identities, agent identity blueprint principals and agents' user accounts. Signals include anomalous sign-ins, reconnaissance of the directory, failed attempts to reach resources the agent isn't authorized for, new credentials added to a blueprint and then used, and Microsoft threat intelligence. Microsoft documents admin actions, **Confirm safe** and **Dismiss risk**, as the way to clear an agent's risk, and until then the signals that triggered the flag have not been addressed. An agent can't be sent through multifactor authentication the way a risky user can: for agent risk, Conditional Access can only block, so the flag is left for an admin to handle. Dismissing a flag clears it but does not remove compromised credentials, so investigate first.

This check reports agents whose risk level is **high** and whose risk state is still active and unremediated (`atRisk` or `confirmedCompromised`). States that represent a handled flag (`dismissed`, `confirmedSafe`, `remediated`, `none`) are not reported. Deleted agents are not reported, because a deleted agent cannot sign in and leaves nothing to act on. Disabled agents are still reported, because disabling only blocks sign-ins: the risk stays open until an admin dismisses it or confirms the agent safe. The check reads risk only and never changes an agent's risk state.

If a reported agent holds a privileged directory role, active or PIM-eligible, the result lists the role and shows that entry first, since a compromised agent with admin rights puts the whole tenant at risk.

The check needs Microsoft Entra ID P2 and Microsoft Agent 365: ID Protection for agents needs P2 during the preview, and Microsoft says it will require Agent 365. Tenants without both skip the check as not licensed. It also needs the Microsoft Graph permission `IdentityRiskyAgent.Read.All`, which Maester does not request by default. Without it the check is skipped. To identify privileged agents, it also reads directory roles, which needs `RoleManagement.Read.Directory` or `RoleManagement.Read.All`. If those reads fail, the agents are still reported with a note. Connect with `Connect-Maester -IncludePreview`, or grant the permission to the app registration that runs Maester.

This is the agent companion to MT.1262, which reports high-risk service principals. Entra ID Protection reports agent risk in its own list, `riskyAgents`, which MT.1262 does not read. MT.1285 reports medium-risk agents.

#### Remediation action

1. Open the [Microsoft Entra admin center](https://entra.microsoft.com) and navigate to **ID Protection** > **Risky agents**.
2. Locate each reported agent by its name or object ID. Start with any agent this check's result lists with a privileged role.
3. Investigate the agent's risk detections (also listed under **Risk detections** > **Agent detections** for up to 90 days), its sign-in logs and audit logs, and the audit logs of its blueprint (for a multi-instance blueprint, **Entra ID** > **Agents** > **Agent blueprints**). Look for sign-ins or resource access the agent shouldn't make, credentials added to its blueprint, and permissions or roles the agent should not have. For a multi-instance agent, also review the blueprint principal's **Access** > **Granted permissions**: permissions the agent inherits from it don't appear on the agent identity. A single-instance agent inherits nothing, so review only what is granted to the agent identity. If the reported agent is an agent user (Type **Agent user** in the result), also review its directory role assignments, group memberships and the permissions granted to it: an agent user can't hold privileged administrator roles, but it can hold custom roles and inherits access from the groups it's in. If you see active misuse, **Disable** the agent before you investigate further.
4. If the agent is compromised:
   - Select **Confirm compromise**, which sets its risk level to high and triggers any risk-based Conditional Access policy that blocks high agent risk, and **Disable** the agent if you haven't already, so it can't sign in while you remediate. Conditional Access doesn't apply when an agent identity blueprint gets a Microsoft Graph token to create agent identities or agents' user accounts, so it can't stop a compromised blueprint from creating new agent identities; disabling the blueprint principal does (next bullets).
   - For an agent user, remove directory roles, group memberships and access it doesn't need. An agent user signs in only with a token issued to its parent agent identity, so the credential and blueprint steps below apply to that parent agent identity. In the last step, re-enable the agent user or delete it if it's no longer needed. Either way, re-enable its parent agent identity if you disabled it, or retire it if it's no longer needed.
   - A single-instance agent has no blueprint principal, inherits no permissions and doesn't appear under **Agent blueprints**. For one, skip the blueprint principal steps below: rotate its blueprint's credentials through Microsoft Graph if it has any, remove permissions and roles granted directly to the agent identity that it doesn't need, then continue with the last step (re-enable or retire).
   - Otherwise, rotate the blueprint's credentials. Agent identities sign in with their blueprint's credentials, which every agent identity created from that blueprint shares. If a blueprint credential was stolen or the blueprint itself may be compromised, first disable the agent identity blueprint principal: that blocks every agent identity created from it and stops new ones being created from it. Then remove the compromised credentials and any credentials you can't account for, and add new ones, preferably federated credentials or certificates rather than client secrets.
   - Remove permissions and roles the agent doesn't need, including permissions it inherits from its blueprint principal. Removing a permission from the blueprint principal removes the inherited permission from every agent identity created from that blueprint; permissions granted directly to an agent identity stay until you remove them there.
   - If you disabled the agent identity blueprint principal and the blueprint is still in use, re-enable it once its credentials are rotated. While it's disabled, none of the agent identities created from it can sign in. If the blueprint is no longer in use, retire it instead of leaving it disabled.
   - Re-enable the agent only after the blueprint's credentials, if any, are rotated, or retire the agent identity if it's no longer needed. If a risk-based Conditional Access policy blocks high agent risk, the agent stays blocked until you dismiss the risk in step 5.
5. When the investigation is done, clear the flag so the agent is no longer reported. If it wasn't compromised and you disabled it during the investigation, re-enable it. For an agent user, remove directory roles, group memberships and permissions it doesn't need before you select **Confirm safe** or **Dismiss risk**.
   - If the detection was a false positive, select **Confirm safe**. This sets the risk level to none and tells ID Protection to avoid flagging similar activity.
   - If the activity was real but expected (a benign true positive), select **Dismiss risk**, so ID Protection keeps flagging similar activity.
   - If a confirmed compromise has been remediated and the risk is no longer relevant, select **Dismiss risk**.
6. Consider a risk-based Conditional Access policy for agents ([Microsoft's template](https://aka.ms/CreateAgentRiskPolicy)) so that risky agents are blocked automatically rather than left waiting for manual review.

#### Known limitations

* **Beta API.** Microsoft publishes the risky agents list (`riskyAgents`) in Microsoft Graph beta only, so its shape can change.
* **Agent type.** The type comes from each item's `@odata.type`, with `identityType` as the fallback. Some of these values are new enum members that Graph returns as `unknownFutureValue` unless the request asks for them, and Maester's Graph requests don't. An agent whose type can't be read is still reported, with the type **Other agent**, but isn't listed on the report's affected objects page.
* **Risk detail.** Microsoft documents the agent values of Risk detail (`adminConfirmedAgentCompromised`, `adminConfirmedAgentSafe`, `adminDismissedRiskForAgent`) as new enum members that Graph returns only when the request asks for them. In testing, Graph returned `adminConfirmedAgentCompromised` without being asked. If Graph does withhold one, the column says so and points to the Risky agents report.
* **Privileged means directory roles.** The Privileged role column lists only built-in directory roles that Microsoft classifies as privileged, active or PIM-eligible. Custom roles and Microsoft Graph application permissions are not checked, so an agent that holds powerful Graph permissions but no privileged built-in role shows `None`. Only roles assigned directly to the agent are matched: a role held through membership of a role-assignable group isn't detected.
* **PIM-eligible roles.** Eligible role assignments are checked only when the tenant has Microsoft Entra ID P2 or Microsoft Entra ID Governance. Otherwise only active assignments are checked, and when the check reports agents the result includes a note saying so.
