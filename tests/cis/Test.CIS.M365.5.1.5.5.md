The default app management policy blocks custom, user-chosen secrets so that new application secrets are always generated by Microsoft Entra ID.

When a person picks the value of a client secret through the API, the result can be short, predictable or reused from elsewhere. Secrets that Microsoft Entra ID generates are long and random, so they cannot be guessed or sprayed.

The restriction only affects secrets that are added after it takes effect. Automation that supplies its own secret value must be changed to use the generated one.

#### Remediation action

1. Connect to Microsoft Graph with an account that has the Global Administrator role, or with the Security Administrator and Application Administrator roles.
2. Retrieve the current default app management policy before sending an update. In each of `applicationRestrictions` and `servicePrincipalRestrictions`, find the `passwordCredentials` entry whose `restrictionType` is `customPasswordAddition`. Modify that entry in place when it exists; add one only when no matching entry exists. Preserve every other `passwordCredentials` entry in both collections in the update. Sending only the target restriction can disable other active restrictions.
3. Set `isEnabled` to `true`. For each matching `customPasswordAddition` entry, set `state` to `enabled` and keep its existing `restrictForAppsCreatedAfterDateTime` only if it is earlier than the oldest object in that collection; otherwise, use a date before that oldest object. When choosing the oldest service principal, treat a null `createdDateTime` as January 1, 2019, as Microsoft Graph does. Apply the same cutoff rule to a new entry. If a collection is empty, use the tenant creation date or an earlier date as its cutoff. Objects created before their collection's cutoff date are exempt.
